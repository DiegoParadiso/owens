# Capítulo 4: Implementación y Aseguramiento de Calidad (QA)

## 4.1 Enfoque Metodológico de Construcción

Para garantizar que el software construido refleje exactamente las necesidades del negocio y minimice la introducción de regresiones (bugs), el proyecto adoptó una estrategia de calidad de tres niveles. Esta estrategia complementa la metodología del Proceso Unificado (UP) guiando el desarrollo del código:

### 1. SDD (Specification-Driven Development)
El desarrollo estuvo **Guiado por Especificaciones**. Antes de la codificación, se diseñaron rigurosamente los Casos de Uso (UC), los Diagramas de Secuencia del Sistema (DSS) y las Matrices de Rastreabilidad. Este documento actuó como el "contrato" único de verdad. Ninguna línea de código fue escrita sin que existiera previamente un requerimiento documentado que lo justificara, asegurando el alineamiento total con los objetivos de la tesis.

### 2. BDD (Behavior-Driven Development)
Las pruebas automatizadas fueron **Guiadas por el Comportamiento**. Utilizando el framework **Cypress**, los Casos de Uso se tradujeron a código utilizando un lenguaje cercano al humano (escenarios de tipo *Dado que... Cuando... Entonces...*). De esta forma, las pruebas no evalúan simples funciones matemáticas, sino que simulan el comportamiento real de los actores (Ej. Cajero, Cocinero) interactuando con la interfaz del sistema.

### 3. TDD (Test-Driven Development)
Durante la implementación de lógicas críticas (como el Control de Acceso Basado en Roles - RBAC y las validaciones de caja), se aplicó el ciclo de **Desarrollo Guiado por Pruebas** (Rojo-Verde-Refactor):
* **Fase Roja:** Se redactaron los escenarios de falla en Cypress (Ej: Validar que un Cocinero no pueda ver el módulo Financiero), obteniendo un fallo intencional que revelaba la vulnerabilidad.
* **Fase Verde:** Se codificó la validación estricta en los Controladores y en el ORM de Laravel para que la prueba pasara con éxito.
* **Refactorización:** Se optimizó la arquitectura (ej. implementando Enrutamiento Inteligente) sin romper las pruebas previamente superadas.

## 4.2 Estrategia de Pruebas (Pirámide de Testing)

El Aseguramiento de Calidad (QA) del Sistema Owens se basó en el concepto de la "Pirámide de Pruebas", balanceando el costo de creación de los tests con el valor de negocio que aportan.

### 1. Pruebas Unitarias (Unit Tests)
* **Alcance:** Evalúan funciones individuales aisladas del resto del sistema (Ej. una función que calcula el total con IVA). 
* **Herramientas:** PHPUnit (Backend) o Jest (Frontend).
* **Justificación de alcance:** Para el alcance de este proyecto, la lógica de negocio se encuentra altamente acoplada al ORM y a la base de datos (Ej. transacciones de inventario). Por ello, el enfoque se desplazó hacia las pruebas de mayor nivel, donde se valida el resultado transaccional completo en lugar de métodos aislados.

### 2. Pruebas de Integración (Integration Tests)
* **Alcance:** Verifican que múltiples componentes funcionen correctamente juntos. En el caso de Owens, evalúan que el frontend en React (Inertia.js) se comunique exitosamente con las API de Laravel y que la base de datos responda de acuerdo a las Reglas de Negocio.
* **Implementación:** Fueron cubiertas implícitamente por Cypress al interceptar las llamadas asíncronas (XHR) durante el ciclo de vida de los componentes, asegurando que la conexión Cliente-Servidor (React -> Laravel -> MySQL) funcione sin fisuras.

### 3. Pruebas End-to-End (E2E)
* **Alcance:** Es el núcleo de la estrategia de QA de este proyecto. Simulan el flujo completo de principio a fin, como lo haría un usuario real en un entorno de producción.
* **Implementación:** Se escribieron suites de pruebas en **Cypress** para los flujos críticos del sistema:
  * *Autenticación y Seguridad:* Pruebas de acceso negativo, positivo y hermetismo de roles (RBAC).
  * *Operatividad de Caja:* Apertura y cierre, validación de montos e interfaz dinámica del POS.
  * *Ingeniería de Menú:* Descuento atómico de inventario (Kardex) mediante validación de explosión de recetas al concretar una venta.
  * *Transacciones Fiscales y Compras:* Aplicación correcta de alícuotas de IVA y simulación de cotizaciones predictivas (Mocks de API para proveedores).
* **Valor para el negocio:** Son la prueba irrefutable ante el cliente (y el tribunal) de que el sistema cumple con los Requisitos Funcionales establecidos en la Etapa de Análisis.

### 4. Pruebas de Despliegue y Aceptación (UAT)
* **Alcance:** Asegurar que el sistema funciona correctamente en el entorno de producción (o *Staging*) y cumple con las expectativas del usuario final en condiciones reales.
* **Implementación:** Involucran pruebas de regresión visual, pruebas en diferentes resoluciones (Responsive Design para KDS vs POS) y la validación final del cliente (Owner). Garantizan que las configuraciones del entorno (`.env`), la conexión a la base de datos de producción y los certificados SSL estén operando correctamente tras el despliegue continuo (CI/CD).
