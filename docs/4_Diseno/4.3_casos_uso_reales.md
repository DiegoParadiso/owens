# 4.3. Casos de Uso Reales

Esta sección especifica la interacción física, tecnológica y ergonómica entre los actores y los componentes de la interfaz gráfica de usuario (GUI), referenciando de manera estricta los identificadores de controles `[1]..[N]` y las pantallas de retroalimentación `[Pantalla A]..[Pantalla M]` definidos en la Sección 4.2.

---

### 4.3.1. CU - 15: Asignar Receta a Producto (Alta de Ficha Técnica)
[Ir al Diseño](4.2_diseno_entrada.md#421-cu---15-asignar-receta-a-producto-alta-de-ficha-tecnica)

| Metadato | Especificación |
| :--- | :--- |
| **Caso de Uso** | CU-15: Asignar Receta a Producto (Alta de Ficha Técnica) |
| **Objetivos asociados** | OBJ-02 (Controlar inventario mediante recetas) |
| **Requisitos asociados** | RF-15 (Ingeniería de Menú y BOM), RNF-01 (Integridad Transaccional) |
| **Descripción** | El caso de uso inicia cuando el administrador solicita registrar un nuevo producto en el catálogo y asociarle su matriz de materias primas (BOM). El sistema valida la integridad de los datos, exige la ratificación obligatoria en un modal emergente y, tras la confirmación, incorpora el plato al catálogo activo habilitando el descuento automático de stock por porción elaborada. |
| **Precondición** | - El usuario inició sesión con privilegios de Administrador.<br>- Existen insumos básicos previamente registrados en el inventario. |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El caso de uso inicia cuando el administrador selecciona la opción "Menú y Recetas" [1] en la barra de navegación lateral. |
| **2** | El administrador presiona el botón de acción principal "+ Alta de Producto" [7] ubicado en la base de la tabla. |
| **3** | El sistema despliega el Área de Trabajo con el Formulario de Metadatos [3] en la sección inferior de la pantalla, posicionando el foco del cursor en el campo "Nombre del Producto". |
| **4** | El administrador completa los campos obligatorios del producto (Nombre, Descripción, Precio de Venta) en el formulario [3]. |
| **5** | El administrador clasifica el producto mediante el combobox "Categoría" [4]. |
| **6** | El administrador selecciona una materia prima en el selector de insumos [5], especifica la proporción de consumo en el input de cantidad [6] y presiona el botón interactivo de agregar línea de receta. |
| **7** | El administrador repite el paso 6 hasta completar la lista de ingredientes que componen la receta y presiona el botón de confirmación "Guardar Producto" [8]. |
| **8** | El sistema comprueba que todos los campos del formulario [3] estén completos, valida que la receta contenga al menos un insumo con cantidad mayor a cero y verifica que el nombre no se encuentre duplicado en la base de datos. Al resultar exitosas las comprobaciones, el sistema interrumpe el flujo y despliega el Modal de Confirmación de Operación [Pantalla E]. |
| **9** | El administrador presiona el botón "ACEPTAR" dentro del Modal de Confirmación de Operación [Pantalla E]. |
| **10** | El sistema registra de manera definitiva el producto y su receta en la base de datos relacional, emite la Alerta de Éxito Transaccional [Pantalla A], oculta el área de trabajo desplegable y actualiza de forma asíncrona la Tabla Principal de Catálogo [9], insertando el nuevo registro en la lista. |

#### Postcondición
El nuevo producto y su composición de materias primas quedan registrados en el sistema, figurando disponible para su comercialización en el Punto de Venta.

#### Excepciones

| Paso | Acción |
| :---: | :--- |
| **4-7** | Si el usuario presiona el botón "Cancelar" [10] del formulario, el sistema detiene el flujo de alta, descarta cualquier dato cargado y oculta el formulario devolviendo el protagonismo a la tabla principal [9]. |
| **8** | Si falta completar algún campo obligatorio del formulario [3] o de la categoría [4], el sistema resalta los contornos de los campos vacíos en color rojo, bloquea el avance y emite la Alerta de Validación de Campos [Pantalla B]. |
| **8** | Si el administrador no incorporó al menos un insumo en la receta o especificó cantidades nulas, el sistema frena la transacción y emite la Alerta de Inconsistencia de Receta [Pantalla C]. |
| **8** | Si el nombre del producto ya existe registrado en la misma categoría, el sistema interrumpe la persistencia y emite la Alerta de Registro Duplicado [Pantalla D]. |
| **8** | Si una vez desplegado el Modal de Confirmación de Operación [Pantalla E] el administrador presiona "CANCELAR", el sistema cierra el diálogo emergente y regresa al operario al formulario [3] con todos los datos y la receta intactos para su edición. |

#### Rendimiento y Estabilidad

| Paso | Cota de tiempo |
| :---: | :--- |
| **3** | Despliegue del formulario inferior < 1 segundo. |
| **10** | Persistencia y actualización reactiva de la grilla < 2 segundos. |

*   **Frecuencia:** Semanal o según actualización de la carta gastronómica.
*   **Estabilidad:** Alta.
*   **Comentarios:** Es mandatorio que el sistema calcule el costo teórico acumulado de la receta sumando los precios unitarios ponderados de cada insumo antes de presentar la pantalla de confirmación.

### 4.3.2. CU - 13: Modificación de Producto y Receta
[Ir al Diseño](4.2_diseno_entrada.md#422-cu---13-modificacion-de-producto-y-receta)

| Metadato | Especificación |
| :--- | :--- |
| **Caso de Uso** | CU-13: Modificación de Producto y Receta |
| **Objetivos asociados** | OBJ-02 (Controlar inventario mediante recetas) |
| **Requisitos asociados** | RF-13 (Edición de Menú), RNF-01 (Consistencia de Datos) |
| **Descripción** | Permite al administrador ajustar precios de venta, descripciones o proporciones de ingredientes de un producto existente. |
| **Precondición** | - El usuario inició sesión con privilegios de Administrador.<br>- Existe al menos un producto registrado en el sistema. |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El caso de uso inicia cuando el administrador selecciona "Menú y Recetas" [1] en la barra de navegación lateral. |
| **2** | El administrador utiliza la barra de búsqueda rápida [2] o los filtros [13] para localizar el producto en la tabla principal [9]. |
| **3** | El administrador hace clic en el Ícono de Edición (Lápiz) [11] ubicado en la fila correspondiente al producto. |
| **4** | El sistema despliega el Área de Trabajo inferior [3], precargando todos los campos con los valores vigentes del producto y dibujando la subgrilla con los insumos actuales de la receta. |
| **5** | El administrador modifica los datos requeridos (ej. nuevo precio de venta o ajuste de cantidades de insumos). |
| **6** | El administrador presiona el botón de confirmación "Modificar Producto" [8]. |
| **7** | El sistema valida que los campos no estén vacíos y que las cantidades sigan siendo coherentes. Tras validar, despliega el Modal de Confirmación de Operación [Pantalla E]. |
| **8** | El administrador presiona "ACEPTAR" en el Modal de Confirmación [Pantalla E]. |
| **9** | El sistema actualiza el registro en la base de datos, emite la Alerta de Éxito Transaccional [Pantalla A], oculta el área de trabajo y refresca la fila en la Tabla Principal [9]. |

#### Postcondición
Los nuevos valores y costos del producto quedan consolidados y vigentes en el sistema.

#### Excepciones

| Paso | Acción |
| :---: | :--- |
| **5** | Si el usuario presiona "Cancelar" [10], el sistema descarta las modificaciones y repliega el formulario sin alterar la base de datos. |
| **7** | Si los datos no superan la validación, emite [Pantalla B] o [Pantalla C] según corresponda. |
| **8** | Si el usuario presiona "CANCELAR" en [Pantalla E], el modal se cierra y el formulario permanece visible con los datos editados. |

| **Descripción** | Permite desactivar lógicamente un producto del menú para que no pueda ser vendido en futuras comandas, preservando la integridad referencial de las ventas pasadas. |
| **Precondición** | El producto se encuentra activo en el catálogo del sistema. |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El administrador localiza el producto en la Tabla Principal [9] utilizando la barra de búsqueda [2]. |

#### Excepciones

| Paso | Acción |
| :---: | :--- |
| **4** | Si el administrador presiona "CANCELAR" en [Pantalla F], el cuadro emergente se destruye y el producto permanece inalterado en estado activo. |

### 4.3.4. CU - 02: Registrar Venta en Punto de Venta (POS)
[Ir al Diseño](4.2_diseno_entrada.md#424-cu---02-registrar-venta-en-punto-de-venta-pos)

| Metadato | Especificación |
| :--- | :--- |
| **Caso de Uso** | CU-02: Registrar Venta en Punto de Venta (POS) |
| **Objetivos asociados** | OBJ-01 (Optimizar atención POS), OBJ-05 (Cumplimiento fiscal AFIP) |
| **Requisitos asociados** | RF-02 (Punto de Venta), RF-47 (Facturación AFIP), RNF-01 (Atomicidad) |
| **Descripción** | El caso de uso inicia cuando el cajero atiende un cliente en el mostrador, selecciona productos en la pantalla táctil, arma la comanda y procesa el cobro emitiendo el ticket fiscal con autorización CAE de AFIP. |
| **Precondición** | - El usuario inició sesión con rol de Cajero.<br>- Existe una sesión de caja activa en estado "Abierta" en el puesto. |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El caso de uso inicia cuando el cajero selecciona la opción "Punto de Venta" [20] en la barra de navegación lateral. |
| **2** | El sistema inicializa una nueva comanda con orden diaria correlativa y presenta la grilla de productos y el panel de ticket vacío [23]. |
| **3** | El cajero pulsa las pestañas de categorías [21] para filtrar y presiona las tarjetas táctiles de productos [22] solicitados por el cliente. |
| **4** | El sistema incorpora cada artículo al panel de ticket en vivo [23], suma la línea y actualiza de forma reactiva el Total a cobrar [25]. |
| **5** | El cajero ajusta cantidades mediante los botones táctiles (+ / -) [24] si es requerido y presiona el botón principal "COBRAR" [26]. |
| **6** | El sistema interrumpe la grilla y despliega el Modal Emergente de Cobro y Facturación, exhibiendo el total adeudado. |
| **7** | El cajero selecciona el medio de pago pulsando el botón correspondiente [27] (ej. "Efectivo"). |
| **8** | El cajero digita el dinero entregado por el cliente en el input numérico [28]. |
| **9** | El sistema calcula instantáneamente el vuelto en el display visual [29]. |
| **10** | El cajero presiona el botón transaccional "Confirmar Pago y Facturar" [30]. |
| **11** | El sistema ejecuta una transacción atómica: solicita autorización fiscal CAE al servicio web de AFIP, descuenta del inventario las materias primas por receta, registra la venta y despliega el Modal de Cobro Exitoso [Pantalla G], disparando la impresión del ticket fiscal. |
| **12** | El cajero entrega el comprobante y el vuelto al cliente, cerrando el modal. La pantalla limpia el ticket y queda lista para el siguiente cliente. |

#### Postcondición
La venta queda cobrada y facturada con CAE, el stock de materias primas queda descontado y la comanda viaja automáticamente al monitor de cocina KDS.

#### Excepciones

| Paso | Acción |
| :---: | :--- |
| **3** | Si no hay stock suficiente de materias primas para elaborar el plato seleccionado, el sistema bloquea el clic y emite la Alerta de Stock Insuficiente [Pantalla H]. |
| **8** | Si el importe digitado en el input [28] es menor al total adeudado, el botón de cobro se bloquea y se emite la Alerta de Pago Insuficiente [Pantalla I]. |
| **11** | Si el Web Service de AFIP no responde tras 3 intentos, el sistema emite el comprobante en modalidad de contingencia offline con leyenda reglamentaria y encola la solicitud para reintento automático en segundo plano. |

### 4.3.5. CU - 05: Anular Venta y Emitir Nota de Crédito
[Ir al Diseño](4.2_diseno_entrada.md#425-cu---05-anular-venta-y-emitir-nota-de-credito)

| Metadato | Especificación |
| :--- | :--- |
| **Caso de Uso** | CU-05: Anular Venta y Emitir Nota de Crédito |
| **Objetivos asociados** | OBJ-01, OBJ-05, OBJ-07 (Auditoría) |
| **Requisitos asociados** | RF-05 (Anulación y Reintegros), RF-47 (Nota de Crédito AFIP) |
| **Descripción** | Permite anular una venta errónea o devuelta, emitiendo la correspondiente Nota de Crédito fiscal y reponiendo el stock de materias primas de forma atómica. |
| **Precondición** | La venta a anular se encuentra registrada en estado "Cobrada". |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El cajero presiona el botón "Buscar y Anular Venta" [31] en el encabezado del Punto de Venta. |
| **2** | El sistema despliega un cuadro de búsqueda flotante. |
| **3** | El cajero ingresa el número de ticket en el input [32] y presiona "Buscar". |
| **4** | El sistema recupera los datos de la venta (fecha, cajero, ítems y total) y los muestra en pantalla. |
| **5** | El cajero tipea el motivo obligatorio de la anulación en el área de texto [33] y presiona "Proceder a Anulación". |
| **6** | El sistema despliega el Modal de Confirmación de Anulación [Pantalla J], advirtiendo sobre la emisión de nota de crédito. |
| **7** | El cajero (o supervisor) introduce su clave de autorización y presiona "ACEPTAR". |
| **8** | El sistema cambia el estado de la venta a "Anulada", genera la Nota de Crédito fiscal en AFIP, reintegra al inventario los insumos deducidos originalmente y emite la Alerta de Éxito [Pantalla A]. |

#### Postcondición
La venta queda cancelada contablemente y los insumos se reincorporan al stock disponible.

### 4.3.7. CU - 03: Cerrar Sesión de Caja (Arqueo con Cierre Ciego)
[Ir al Diseño](4.2_diseno_entrada.md#427-cu---03-cerrar-sesion-de-caja-arqueo-con-cierre-ciego)

| Metadato | Especificación |
| :--- | :--- |
| **Caso de Uso** | CU-03: Cerrar Sesión de Caja (Arqueo con Cierre Ciego) |
| **Objetivos asociados** | OBJ-01, OBJ-07 (Auditoría Financiera) |
| **Requisitos asociados** | RF-03 (Arqueo de Caja con Cierre Ciego), RNF-04 (Seguridad) |
| **Descripción** | Clausura el turno operativo obligando al cajero a realizar el conteo físico de gaveta sin revelarle el saldo teórico esperado por el sistema. |
| **Precondición** | Existe una sesión de caja abierta a nombre del cajero. |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El cajero selecciona la opción "Caja y Turno" [40] y hace clic en "Cierre de Turno". |
| **2** | El sistema despliega la Grilla de Conteo Físico Ciego [43], ocultando deliberadamente el total de ventas del día. |
| **3** | El cajero cuenta el dinero en gaveta e ingresa la cantidad de billetes por denominación en la grilla [43]. |
| **4** | El sistema calcula automáticamente la sumatoria en el Display "Total Físico Declarado" [44]. |
| **5** | El cajero verifica el monto declarado y presiona el botón "Confirmar Cierre de Caja" [45]. |
| **6** | El sistema bloquea el turno, calcula la diferencia (conteo físico vs. fondo inicial + ventas en efectivo), asienta el arqueo inmutable en base de datos y despliega el Modal de Resultado de Arqueo [Pantalla L] exhibiendo el balance final. |

#### Postcondición
La sesión queda en estado "Cerrada", inhabilitando nuevas ventas hasta la próxima apertura de turno.

### 4.3.9. CU - 29: Generar Reporte Consolidado de Ventas y Rendición de Caja
[Ir al Diseño](4.1_diseno_salida.md#411-cu-29-generar-reporte-consolidado-de-ventas-y-caja)

| Metadato | Especificación |
| :--- | :--- |
| **Caso de Uso** | CU-29: Generar Reporte Consolidado de Ventas y Rendición de Caja |
| **Objetivos asociados** | OBJ-06 (Decisiones gerenciales), OBJ-07 (Auditoría) |
| **Requisitos asociados** | RF-29 (Reportes Financieros), RNF-04 (Seguridad) |
| **Descripción** | Permite al administrador o auditor consultar el rendimiento comercial y las diferencias de caja en pantalla o exportar el documento formal en formato PDF estandarizado. |
| **Precondición** | El usuario inició sesión con privilegios de Administrador o Auditor. |

#### Secuencia normal

| Paso | Acción |
| :---: | :--- |
| **1** | El usuario selecciona la opción "Reportes y Auditoría" en la barra de navegación lateral. |
| **2** | El sistema despliega la Interfaz de Consulta de Ventas (Figura N° 4.1.1.1), posicionando por defecto el rango de fechas en el mes en curso. |

| **5** | El usuario analiza la información en pantalla y presiona el botón de acción superior "Exportar a PDF". |

#### Postcondición
El reporte financiero queda generado y descargado en el equipo del cliente, registrando una entrada inmutable en la bitácora de auditoría del sistema.
