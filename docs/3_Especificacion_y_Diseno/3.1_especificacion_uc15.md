### 3.2 Especificación de Casos de Uso Críticos

#### Caso de Uso: UC-15 Asignar Receta a Producto

**Objetivos Asociados**
*   **OBJ-02** Controlar el inventario mediante recetas.


**Actor Principal**
Administrador.

**Precondición**
*   El usuario inició sesión en el sistema (`<<extend>> UC-36`).
*   Tanto el producto final como los insumos (ingredientes) ya deben estar registrados previamente.

**Intención del Actor**
Definir la composición exacta de un producto final (ej. Hamburguesa) indicando qué insumos y en qué cantidades lo conforman, para que el sistema descuente el stock automáticamente al registrarse una venta.

**Propósito del Sistema**
Persistir la estructura jerárquica de la receta, verificando la consistencia, garantizando que los ingredientes existan y validando que no se generen estructuras lógicas imposibles (ej. que un producto sea ingrediente de sí mismo).

**Descripción General**
El Administrador selecciona un producto final y agrega uno o más productos insumo, definiendo la cantidad necesaria de cada uno. El sistema valida las reglas de integridad jerárquica y consolida la receta.

**Secuencia Normal**
| Paso | Acción |
| :--- | :--- |
| 1 | El caso de uso inicia cuando el Administrador solicita asignar una receta a un producto (producto padre). |
| 2 | El Sistema solicita seleccionar los ingredientes (productos hijos). |
| 3 | El Administrador selecciona uno o más ingredientes e ingresa la cantidad necesaria de cada uno. |
| 4 | El Sistema verifica que los productos seleccionados (padre e hijos) existan y se encuentren en estado activo. |
| 5 | El Sistema verifica que no existan estructuras lógicas imposibles (ej. que un ingrediente se contenga a sí mismo) en la receta definida. |
| 6 | El Sistema asocia los insumos al producto padre, actualiza el indicador de "compuesto por receta" y consolida los cambios. |
| 7 | El Sistema notifica al Administrador que la receta se guardó exitosamente y finaliza el caso de uso. |

**Postcondición**
*   El producto final quedó configurado como un artículo compuesto.
*   Las relaciones de la receta fueron almacenadas permanentemente.

**Excepciones**
| Paso | Acción |
| :--- | :--- |
| 4 | **Insumo Inexistente/Inactivo:** Si el sistema detecta que algún ingrediente fue eliminado (Soft Delete) o no existe, detiene la operación y notifica al usuario. **El caso de uso regresa al paso 2.** |
| 5 | **Estructura Inválida Detectada:** Si se detecta que el producto padre figura directa o indirectamente como ingrediente de sí mismo, el sistema bloquea la asignación por inconsistencia lógica y alerta al usuario. **El caso de uso regresa al paso 2.** |

**Rendimiento**
| Paso | Cota de tiempo |
| :--- | :--- |
| 5 | Validación de estructura de receta < 1 segundo. |

**Frecuencia**
Baja (Generalmente al dar de alta nuevos productos en el menú).

**Estabilidad**
Alta.

**Comentarios**
Este caso de uso es crítico para el correcto funcionamiento del motor de inventario.
