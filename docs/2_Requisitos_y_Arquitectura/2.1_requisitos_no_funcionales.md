# 2. Requisitos y Arquitectura

## 2.1 Requisitos No Funcionales y Seguridad

A diferencia de los requerimientos funcionales que describen el *qué* hace el sistema (capturados en los Casos de Uso), los Requisitos No Funcionales describen el *cómo*. Estos requerimientos dictan los atributos de calidad, rendimiento, confiabilidad y soporte del sistema, constituyendo las fuerzas principales que moldean la Arquitectura de Software.

Para documentar exhaustivamente estos atributos de calidad, el proyecto adopta la clasificación estándar de la industria **FURPS+** (*Functionality, Usability, Reliability, Performance, Supportability* y restricciones adicionales de diseño y normativas), reconocida internacionalmente y recomendada por expertos en ingeniería y arquitectura de software (Eeles & Cripps, 2010; Larman, 2004).

A continuación se presentan las especificaciones formales de los Requisitos No Funcionales del Sistema Owens:

| Campo | Detalle de Especificación |
| :--- | :--- |
| **ID** | **NFR-01** |
| **Nombre** | **Rendimiento y Tiempos de Respuesta** |
| **Categoría** | Rendimiento (*Performance*) |
| **Descripción** | El módulo de Punto de Venta (POS) debe procesar la adición de productos al carrito y el cálculo de subtotales e impuestos en un tiempo menor a 1 segundo para no retrasar la atención al cliente. |
| **Justificación** | En un entorno Fast-Food de atención rápida por mostrador, la velocidad de despacho es crítica para la rentabilidad y satisfacción del cliente. |

### Tabla 78
**Requisitos No Funcionales: Continuidad Operativa (Tolerancia a Fallos)**

| Campo | Detalle de Especificación |
| :--- | :--- |
| **ID** | **NFR-02** |
| **Nombre** | **Continuidad Operativa (Tolerancia a Fallos)** |
| **Categoría** | Confiabilidad (*Reliability*) |
| **Descripción** | Ante una desconexión temporal con los servidores de AFIP o corte de enlace externo, el sistema debe permitir registrar las ventas en estado "Pendiente" e imprimir un ticket de control interno en la red local, encolando la facturación fiscal para su posterior procesamiento por lotes al restablecerse la conectividad. |

### Tabla 79
**Requisitos No Funcionales: Seguridad de Acceso y Datos**

| Campo | Detalle de Especificación |
| :--- | :--- |
| **ID** | **NFR-03** |
| **Nombre** | **Seguridad de Acceso y Datos** |
| **Categoría** | Seguridad (*Security*) |
| **Descripción** | El sistema debe implementar un control de acceso basado en roles (RBAC). Las contraseñas deben ser almacenadas mediante algoritmos de derivación unidireccional (*Bcrypt* / Argon2). Todas las acciones sensibles de modificación, eliminación o anulación de transacciones deben quedar registradas en una pista de auditoría inmutable indicando fecha, usuario, entidad y valores anteriores y posteriores (*Audit Trail* polimórfico). |
| **Justificación** | Prevención de fraudes internos, mitigación de accesos indebidos y garantía de transparencia contable y financiera. |
